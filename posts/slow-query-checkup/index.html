从一个慢查询开始：给个人项目做一次性能体检

一次没有复杂工具链的排查：先确认体感，再找到证据，最后只改真正拖慢页面的那一段。

个人项目最容易出现两种性能问题：一种是真的慢，另一种是我们觉得它应该很快。前者需要优化，后者需要测量。这个周末，我决定把首页偶尔出现的两秒空白认真查完。

先记录体感，再建立基线

我没有第一时间改代码，而是固定了一组最常见的操作：冷启动、打开首页、切换归档、搜索一篇文章。每个动作跑五次，记录中位数，同时把服务端日志里的查询耗时单独列出来。

const startedAt = performance.now();
const posts = await db.query.posts.findMany({ with: { tags: true } });
console.info("posts.query", Math.round(performance.now() - startedAt));

很快，问题从“首页有点慢”缩小成了一个明确事实：文章列表的数据库查询只需要 36ms，但标签统计触发了逐篇查询。页面上只有一个小小的热门标签区，却承担了主要等待时间。

只改证据指向的部分

最终的修复并不戏剧化。我把标签计数改成一次聚合查询，为结果加上五分钟缓存，并延后加载首页视口外的统计模块。冷启动时间从 1.8 秒降到 420 毫秒，热访问稳定在 150 毫秒以内。

性能优化最有价值的部分不是数字变漂亮，而是建立一条可以重复的路径：描述问题、固定场景、采集证据、做最小改动，再回到同一组场景验证。

工程判断往往不是“还能优化什么”，而是“现在最值得优化的是什么”。

这次体检也留下了一个小规则：每加一个首页模块，都要回答它是否值得进入首屏关键路径。很多漂亮功能，本来就可以晚一点出现。
